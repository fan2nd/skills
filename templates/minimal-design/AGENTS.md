## 设计与实现

- 编码前依次完成需求梳理、架构设计、UI/UX 设计（涉及界面时）。每个阶段都必须与用户沟通，汇总方案并获得用户明确确认后，才能进入下一阶段。所有适用设计阶段确认后才能编码。
- 需求阶段明确目标、范围、关键行为和验收标准。架构与 UI/UX 阶段说明设计方案、依据及与需求的对应关系，解决影响下一阶段的疑问。设计深度与任务规模相称。
- 用户提出需求时，必须主动分析其实际目标、完整使用流程、关联场景和同类需求，提出有依据的补充建议及取舍，交由用户确认范围。禁止仅围绕用户举出的单个例子或局部症状直接定方案。
- 设计必须覆盖已确认场景中的共性需求，明确适用范围与变化点，优先采用可复用的流程、数据模型和接口。禁止为单个示例硬编码或为同类场景重复实现。通用性须有具体场景支撑，新增能力经用户确认后纳入实现。
- 已有明确确认的结论沿用，变更时重新确认受影响部分，并在 `dhf/` 记录各阶段确认结论。不得以自行推断、用户未回复或模型自行判定闭环代替用户确认。
- 禁止擅自新增限定条件或收窄已确认的需求范围。需要增加输入限制、数量上限、适用条件、前置要求或操作约束时，必须先说明依据、影响和可选方案，与用户讨论并获得明确确认后才能采用。发现客观技术限制时也须及时告知并协商方案，禁止以实现方便或防御性考虑自行设限。
- 需求、架构设计、UI/UX 设计、验证记录等文档统一保存在项目根目录的 `dhf/` 中，随实现同步更新。
- 在 `dhf/` 维护需求跟踪表，为需求分配稳定编号，关联设计、实现位置、验收标准和验证结果，并记录状态与变更。交付前逐项核对，验证通过后标记完成。
- 技术选型优先 Rust，避免 C 与 Rust 混编。只在项目有具体用途时引入 Python 脚本。
- 从当前核心流程出发，选择满足需求的最简单实现。新增抽象、配置或扩展点应有明确用途。
- 修改代码时优雅第一，优先保证结构清晰、职责合理和长期可维护性。禁止为了缩小 diff 或减少改动文件而保留不合理结构、堆叠补丁或重复逻辑。需要重构时应完整梳理受影响的调用链并同步调整，在已确认需求范围内保留调用方依赖的行为。
- 修复问题时必须在整个项目中排查相同根因、相似实现及相关调用路径，统一修复已确认的同类问题并验证受影响场景。禁止只修复报错位置或用户指出的一处就结束。涉及需求变化时先与用户确认。
- 在系统边界校验输入，内部代码信任已验证的约定。只为明确的失败场景添加兜底、重试或兼容逻辑，让无法处理的错误向上传播。
- 测试应验证真实业务行为、关键边界或已知回归风险。避免验证语言常识、重复实现逻辑或仅为凑覆盖率编写的测试，每个测试都应能说明它能发现什么实际错误。

## 界面

- UI 简洁高效。只保留完成操作所需的标签、提示和反馈，删去重复说明和装饰性文案。
- 非浏览型界面必须在支持的窗口尺寸内单屏展示，禁止页面和局部容器滚动。内容放不下时，精简布局或拆分视图，确保控件完整可见、可操作。
- 桌面 GUI 调用后台程序时避免弹出控制台。打包使用图形应用入口，确保双击应用或快捷方式时没有终端窗口闪现。
