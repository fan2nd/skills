## 设计与实现

- 开始任务时必须先与用户沟通需求，明确目标、范围、关键行为和验收标准，汇总需求并获得用户明确确认后，才能进入架构设计和后续实现。已有明确确认的需求沿用，需求变更时确认受影响部分。不得以自行推断或用户未回复视为确认。
- 编码前依次完成需求梳理、架构设计、UI/UX 设计（涉及界面时）。每阶段明确结论、依据和验收标准，解决影响下一阶段的疑问并核对前后设计一致后，再进入下一步。设计深度与任务规模相称。
- 需求、架构设计、UI/UX 设计、验证记录等文档统一保存在项目根目录的 `dhf/` 中，随实现同步更新。
- 在 `dhf/` 维护需求跟踪表，为需求分配稳定编号，关联设计、实现位置、验收标准和验证结果，并记录状态与变更。交付前逐项核对，验证通过后标记完成。
- 技术选型优先 Rust，避免 C 与 Rust 混编。只在项目有具体用途时引入 Python 脚本。
- 从当前核心流程出发，选择满足需求的最简单实现。新增抽象、配置或扩展点应有明确用途。
- 重构只解决具体问题，保留调用方依赖的行为。
- 在系统边界校验输入，内部代码信任已验证的约定。只为明确的失败场景添加兜底、重试或兼容逻辑，让无法处理的错误向上传播。
- 测试应验证真实业务行为、关键边界或已知回归风险。避免验证语言常识、重复实现逻辑或仅为凑覆盖率编写的测试，每个测试都应能说明它能发现什么实际错误。

## 界面

- UI 简洁高效。只保留完成操作所需的标签、提示和反馈，删去重复说明和装饰性文案。
- 非浏览型界面必须在支持的窗口尺寸内单屏展示，禁止页面和局部容器滚动。内容放不下时，精简布局或拆分视图，确保控件完整可见、可操作。
- 桌面 GUI 调用后台程序时避免弹出控制台。打包使用图形应用入口，确保双击应用或快捷方式时没有终端窗口闪现。
